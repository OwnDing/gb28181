## 1. 背景与目标

当前 GB28181 项目的后端、Web 前端和 AI 配套能力已经开发完成，现阶段目标是在不推翻现有系统的前提下，新增一套移动端 App 交付方案。

本次 App 方案目标如下：

- 将当前前端已有的核心功能映射为一套适合手机使用的移动端页面。
- 在项目根目录下的 `app/` 新建 Expo 工程，作为跨端 App 客户端。
- App 采用 `WebView + 移动端 H5` 的模式承载业务页面，尽可能复用现有后端接口和前端业务逻辑。
- 首期优先实现可上线、可演示、可持续迭代的版本，而不是一次性追求大量原生能力。

本方案的核心判断是：

- 不建议直接把现有桌面 Web 管理台页面原样放进手机 WebView。
- 更合理的方式是复用后端接口，单独做一套移动端 H5 页面，再由 Expo 壳承载。

## 2. 当前项目现状评估

### 2.1 后端现状

当前后端为 Java Spring Boot 项目，主端口为 `8081`，已具备以下能力：

- 登录鉴权
- 设备管理

- 实时预览

- 报警记录

接口能力已经较完整，足以支撑首版移动端开发。

### 2.2 Web 前端现状

当前前端为 React + Vite 单页应用，主要页面包括：

- 登录
- 设备管理
- 在线预览
- 录像回看
- 存储设置

因此，现有前端不适合直接在手机 WebView 中原样展示。

### 2.3 App 容器现状

项目根目录下已经有空目录：

- `app/`

这非常适合直接作为 Expo 工程目录使用。

### 2.4 参考项目现状

参考 Expo 项目 `sunlight-app` 已经具备较成熟的壳层实现思路：

该项目可作为当前 App 壳层的实现参考。

## 3. 总体设计原则

本次 App 建设遵循以下原则：

- 复用优先：优先复用现有后端接口和已有业务逻辑。
- 分层清晰：业务主要放在移动端 H5，Expo 负责容器能力。
- 快速上线：先完成可用版本，再逐步接入原生增强能力。
- 双端并存：PC 管理台与移动端页面共用同一后端，但前端页面独立设计。
- 可持续演进：后续如果需要，也可以从 WebView 模式逐步演进到部分原生页面。

## 4. 推荐总体方案

## 4.1 方案结论

推荐采用以下架构：

- 在现有 `frontend/` 中新增一套移动端 H5 页面。
- 移动端页面使用独立路由，例如 `/m/*`。
- 在 `app/` 中创建 Expo 工程。
- Expo App 使用 WebView 打开移动端 H5 页面。
- App 首版以“壳应用”定位为主，后续逐步增加原生增强能力。

## 4.2 架构分层

整体分为三层：

### A. 后端服务层

职责：

- 提供业务 API
- 提供鉴权能力
- 提供媒体播放相关接口
- 提供报警、存储、GB28181 等业务能力

### B. 移动端 H5 业务层

职责：

- 实现适合手机操作的业务页面
- 处理登录态、接口请求、页面路由、业务交互
- 作为 Expo WebView 实际承载的内容

### C. Expo 原生壳层

职责：

- App 启动页
- WebView 容器
- 环境地址配置
- 网络异常提示
- Android 返回键处理
- WebView 与原生桥接
- 后续推送、文件分享、扫码、下载等能力接入

## 4.3 为什么不直接复用当前桌面页面

如果直接在 App WebView 中访问当前桌面前端，会产生以下问题：

- 顶部导航和左侧菜单在手机上占用空间过大。
- 表格页面在手机屏幕上可读性差。
- 弹窗交互在小屏设备上不自然。
- 多路视频预览会严重挤压画面区域。
- 某些桌面浏览器假设在移动 WebView 中不成立。

因此，推荐“业务复用、页面重做”，而不是“页面强行缩放”。

## 10. 视频播放技术方案

视频能力是本项目移动端最关键的技术点，必须单独设计。

## 10.1 实时预览协议策略

推荐首版策略如下：

| 平台 | 首选协议 | 备选协议 | 说明 |
|---|---|---|---|
| iOS WebView | HLS | WebRTC | iOS 对原生视频播放兼容性更稳 |
| Android WebView | WebRTC | HLS / HTTP-FLV | 低时延场景优先 WebRTC |
| H.264 流 | WebRTC / HLS / FLV | Jessibuca | 兼容性较好 |
| H.265 流 | HLS 或经过能力判断后播放 | Jessibuca/WASM | 需重点验证机型兼容性 |

结论：

- 不应把桌面端浏览器能力假设直接照搬到手机 WebView。
- 移动端需要单独做协议选择逻辑。

## 10.2 Jessibuca 使用建议

当前前端已经接入：

- `jessibuca.js`
- `decoder.js`
- `decoder.wasm`

移动端可继续保留 Jessibuca 作为补充方案，但不建议把它作为所有设备、所有协议、所有机型的唯一方案。

建议角色：

- H.264/H.265 特定场景的兜底方案
- 兼容某些 WebRTC 不稳定场景

## 10.3 多路预览策略

桌面端支持多路预览，但移动端建议限制：

- 首版默认单路预览
- 支持 2 分屏或 4 分屏作为增强项
- 不建议首版直接做桌面级多路管理

这样可以减少：

- WebView 内存压力
- 播放器实例数量
- 发热和掉帧风险

## 10.4 录像回放策略

当前 Web 前端的回放实现，是前端先带鉴权请求 MP4，再转换为 blob URL 进行播放。

该方案在手机端存在以下风险：

- 长视频内存占用高
- 加载时间长
- WebView 稳定性下降

因此建议：

- 首版先验证现有方案是否可接受
- 第二阶段优先优化为更适合移动端的直连播放方式
- 必要时新增专门的移动端回放接口

## 11. 鉴权与状态管理方案

## 11.1 首版鉴权方案

首版建议继续沿用当前 Bearer Token 方案。

流程如下：

- H5 登录页调用 `/api/auth/login`
- Token 存储在 H5 环境
- H5 所有接口继续通过 `Authorization: Bearer xxx` 访问

优势：

- 复用现有逻辑
- 无需修改后端鉴权模型
- 开发成本最低

## 11.2 App 与 H5 的关系

建议首版由 H5 独立管理登录态，Expo 只做容器层。

后续如果需要增强，可逐步接入：

- 原生保存服务器地址
- 原生保存用户信息
- 原生发消息给 WebView
- WebView 回传登录态与页面状态

## 12. Expo 壳层设计方案

## 12.1 技术栈建议

推荐：

- Expo
- TypeScript
- expo-router
- react-native-webview
- react-native-safe-area-context

这与参考项目技术方向一致，便于复用经验。

## 12.2 Expo 壳层职责

Expo 不承载主要业务页面，只承载以下能力：

- WebView 页面加载
- 服务器地址配置
- 加载态
- 错误态
- 重试
- Android 返回键
- 状态栏和安全区适配
- 后续原生桥接

## 12.3 WebView 建议能力

建议首版至少具备：

- `javaScriptEnabled`
- `domStorageEnabled`
- `allowsInlineMediaPlayback`
- 错误页展示
- HTTP 错误展示
- 手动重试
- 加载指示器

## 12.4 地址配置建议

建议参考 `sunlight-app` 的做法：

- 开发环境通过 `EXPO_PUBLIC_*` 环境变量配置 H5 地址
- 模拟器与真机分别提供默认地址
- 支持局域网开发调试

建议配置项：

- `EXPO_PUBLIC_GB28181_EMBED_URL`

示例含义：

- 开发期指向 `frontend` 本地开发地址
- 生产期指向部署后的移动端 H5 地址

## 12.5 WebView 打开地址建议

建议 App 打开的不是桌面首页，而是移动端首页，例如：

- `http://<host>:5173/m/home?embed=1&shell=native`

参数说明：

- `embed=1`：表示当前运行在嵌入容器中
- `shell=native`：表示当前来自 Expo 壳

这些参数可用于 H5 做差异化处理，例如：

- 隐藏浏览器专属元素
- 适配原生壳返回逻辑
- 打开桥接能力

## 13. H5 与原生桥接规划

首版可以不大量依赖桥接，但建议预留统一桥协议。

后续桥接可支持：

- 原生向 H5 发送服务器配置
- H5 通知原生当前页面标题
- H5 通知原生是否允许返回
- 原生触发 WebView 刷新
- H5 请求原生分享图片或文件
- H5 请求原生打开扫码页

建议采用 `postMessage` 双向通信，定义统一消息格式：

```json
{
  "type": "page-ready",
  "payload": {
    "route": "/m/home"
  }
}
```

## 14. 后端与部署配套建议

## 14.1 路由回退

如果移动端 H5 使用单页路由，后端或静态服务层需要支持路由回退。

否则以下场景会有风险：

- App 直接打开 `/m/home`
- 用户刷新移动端页面
- 从报警页深链进入详情页

建议后续补充：

- 非 `/api/*` 请求统一回退到前端 `index.html`

## 14.2 移动端资源构建

建议移动端 H5 与桌面端 H5 仍然共用一个 Vite 工程进行构建。

优点：

- 复用现有工程能力
- 复用组件和接口层
- 降低维护成本

## 14.3 服务器地址问题

由于 Expo 真机调试常常运行在局域网环境，需要明确以下地址：

- 前端开发地址
- 后端 API 地址
- ZLM 地址
- 局域网可访问地址

后续开发时需要统一一份调试说明，避免模拟器、真机和本机访问地址不一致。

## 15.2 第二阶段：核心业务闭环

目标：

## 16. 风险点与应对

## 16.1 风险：H.265 在移动 WebView 中兼容性不稳定

应对：

- 做协议降级策略
- 提前验证 iOS 与 Android 真机
- 必要时优先 HLS 或其他兼容方案

## 16.2 风险：多路预览导致卡顿和发热

应对：

- 首版以单路为主
- 限制同时播放路数
- 做页面离开自动停止播放

## 16.3 风险：录像回放现有 blob 方案在手机端内存开销较大

应对：

- 首版先验证
- 第二阶段优化为更适合移动端的回放方式

## 16.4 风险：桌面 UI 代码与移动 UI 混杂

应对：

- 独立 `mobile/` 目录
- 独立布局
- 保持复用接口层，不强行复用页面结构

## 16.5 风险：WebView 环境与浏览器环境差异

应对：

- 增加 `embed=1&shell=native` 环境判断
- 单独做移动端播放和交互适配

## 17. 首版验收标准建议

满足以下条件即可认为首版 App 方案落地成功：

- 能在 `app/` 中启动 Expo 工程
- App 能通过 WebView 打开移动端 H5
- 支持登录和退出登录
- 支持查看设备列表
- 支持查看单路实时预览
- 支持查看报警列表与快照
- 支持基础 PTZ 控制
- 页面在 Android 和 iOS 真机上可正常使用

## 18. 推荐的下一步开发顺序

在本方案确认后，建议按以下顺序开始开发：

1. 在 `app/` 下初始化 Expo 工程骨架。
2. 在 `frontend` 中新增移动端路由和布局。
3. 完成移动端登录页和首页。
4. 完成设备页和预览页。
5. 完成报警页。
6. 再补回放、设置和 GB28181 高级页。

## 19. 最终结论

当前项目最合适的 App 路线是：

- 后端继续复用
- 业务接口继续复用
- 前端新增一套移动端 H5 页面
- `app/` 使用 Expo 做 WebView 壳层

这套方案的优点是：

- 改造成本可控
- 上线速度快
- 风险相对低
- 与现有系统兼容性高
- 后续可逐步增强原生能力

该方案适合作为当前项目的正式 App 建设路线。
